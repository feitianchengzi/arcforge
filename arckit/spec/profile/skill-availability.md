# Skill 可用性策略

## 功能概述

Skill 可用性策略让用户在同一个正式 Skill 项目中维护不同使用方式的 skill，并在应用配置组时决定 skill 对 agent 是日常可见还是仅在用户主动请求后加载。

该策略覆盖用户级常驻、项目级常驻和用户级按需三种消费场景。正式 Skill 项目仍是维护源；用户目录、项目目录和按需目录中的副本都是可重新生成的应用结果。

ArcForge 只负责生成应用结果、维护本地目录和提供按需入口，不充当 agent runtime。按需 skill 的实际执行仍由当前 agent 完成，并继续受 agent 自身的权限、工具和指令边界约束。

## 两个策略维度

Skill 的使用方式由作用域和暴露方式两个策略维度组成，并受合法组合约束。

### 作用域

- `user`：skill 可供该用户的多个项目使用。
- `project`：skill 只供一个明确项目使用。

### 暴露方式

- `ambient`：skill 位于 agent 原生发现目录，agent 在日常任务中可以按自身规则判断是否使用。
- `on-demand`：skill 位于用户级 ArcForge catalog，不进入 agent 原生发现目录；只有用户主动调用按需入口后，agent 才读取其描述和完整指令。

`ambient` 支持 `user` 和 `project` 作用域，`on-demand` 只支持 `user` 作用域。系统不接受 `project + on-demand` 组合。同一个 skill 在不同配置组或不同应用关系中可以采用不同的合法组合。

## 常见使用类型

| 使用类型 | 作用域 | 暴露方式 | 行为 |
|---|---|---|---|
| 日常通用 skill | `user` | `ambient` | 在所有项目的日常任务中可被 agent 自动判断和使用 |
| 项目专用 skill | `project` | `ambient` | 仅在目标项目中可被 agent 自动判断和使用 |
| 用户级按需 skill | `user` | `on-demand` | 对多个项目可用，但只在用户主动调用按需入口后加载 |

三种业务分类不是不可覆盖的 skill 固有类型。正式 Skill 项目可以维护推荐策略，消费端配置组和应用操作负责解析最终策略。推荐策略不写入 `SKILL.md` 并对所有使用者永久生效。

## 维护源推荐策略

正式 Skill 项目在仓库内维护可版本控制的可用性策略清单。该清单随 Git review、分支、版本和发布内容长期演进，不依赖某个维护者机器上的 `~/.arcforge/projects` 本地状态。

维护者可以为整个 Skill 项目声明默认推荐策略，并为特定 skill 声明逐项覆盖。每个推荐值只能是用户级常驻、项目级常驻或用户级按需。

ArcForge 扫描 Skill 项目时，把来源推荐策略和 skill 列表一起纳入工作区快照。新增 skill 没有逐项策略时使用项目默认值；既没有逐项策略也没有项目默认值时标记为未分类，并在审计、应用计划和发布准备中提示维护者补充。

清单中引用不存在 skill 的条目属于失效配置。Skill 改名、移动或删除后，系统不会把旧条目静默绑定到另一个 skill。

来源推荐策略是默认输入，不是对消费端的强制策略。最终应用策略按以下优先级解析：

1. 本次应用操作中的显式选择。
2. 消费端配置组中的逐项覆盖或默认策略。
3. 正式 Skill 项目中的逐项推荐策略。
4. 正式 Skill 项目中的项目默认推荐策略。

上述层次都没有提供策略时，该 skill 保持未分类。Availability-aware 应用计划不会根据调用方是否提供项目目标目录来推断用户级或项目级，也不会静默使用 ambient 兼容值。Agent 或用户需要在本次应用中提供显式选择。旧版直接目标复制流程可以继续保持原目标语义，但不会被解释为来源推荐策略。

应用计划展示来源推荐策略、覆盖来源和最终策略。最终策略与来源推荐不同时，系统保留覆盖并明确显示差异，不把它当作 skill 内容漂移。

维护者修改推荐策略不会静默移动已经安装的 skill。ArcForge 把该变化报告为策略漂移，并生成从旧位置迁移到新位置的应用计划；涉及删除旧副本时继续要求明确确认。

共享和发布正式 Skill 项目时，可版本控制的推荐策略清单随项目一起交付。用户级覆盖、目标路径历史和本地应用关系不进入共享清单。

## 配置组策略

配置组除技能选择外，还可以为选中的 skill 提供消费端默认策略和逐项覆盖。没有消费端覆盖时，系统优先采用维护源推荐策略。

每个最终选中的 skill 必须能够解析出唯一的作用域和暴露方式。系统拒绝作用域、暴露方式或目标 agent 无法确定的应用计划，也拒绝把按需 skill 配置为项目级作用域。

配置组中的通配选择可以使用统一默认策略。需要不同策略的 skill 使用逐项覆盖，不要求为了安装位置不同而复制 skill 维护源。配置组没有声明默认策略时，不会遮蔽维护源推荐策略。

维护源和消费端都未声明可用性策略时，配置组保留未分类状态。应用计划展示缺少的判断，并允许 Agent 或用户在本次操作中补充逐项选择；该选择不反向改写维护源推荐。

配置组和应用计划展示每个 skill 的最终作用域、暴露方式、目标 agent 和解析后的目标位置。用户可以在执行前发现不符合预期的常驻或按需项。

## 项目适用性

维护源可以为 `project-ambient` skill 维护项目适用性数据。该数据只定义 JSON 结构，内容由维护者在 Agent 中根据 skill 的真实能力动态生成和长期维护。

项目适用性包含自然语言摘要、必需条件、偏好条件、排除条件、证据指引和可选澄清问题。字段不限定为编程语言、框架、包管理器或代码项目；非代码、研究、内容、设计和运营类 skill 可以描述各自领域的适用条件。

ArcForge 核心只校验字段类型、标识唯一性和条件结构，不使用关键词、文件名或预置业务枚举判断条件是否满足。Agent 在具体项目中读取条件、检查可用证据、提出必要问题，并生成包含结论、逐项证据、不确定项和说明的适用性评估。

项目级应用计划可以携带 Agent 生成的适用性评估，或记录用户的显式人工覆盖。既没有评估也没有人工覆盖时，计划明确标记尚未评估；执行层不会伪造“适合”结论。Desktop 在确认前展示维护源条件、评估状态和覆盖来源。

## 应用位置

### 常驻位置

用户级常驻 skill 应用到目标 agent 的用户级原生 skill 目录。

项目级常驻 skill 应用到目标项目内目标 agent 的原生 skill 目录。

常驻位置沿用目标应用与漂移功能中的 Agent 目标解析规则。ArcForge 不创建另一套常驻目录约定。

### 按需位置

用户级按需 skill 应用到：

`~/.arcforge/catalog/<source-key>/<skill-name>/`

`source-key` 是本地应用关系中稳定、路径安全的来源标识。它用于避免不同维护源中的同名 skill 相互覆盖，不充当公共 registry 命名空间。

每个 catalog 根目录包含本地索引。索引记录 skill 名称、限定名称、维护源、配置组、应用作用域、实际路径、内容摘要、应用时间和可选别名。索引不复制完整 `SKILL.md` 内容，也不把全部按需 skill 描述暴露给 agent 的日常上下文。

Catalog 内容和索引是由维护源重新生成的用户级本地应用结果，不成为正式维护源；团队共享的是正式 Skill 项目和配置策略。

ArcForge 不把按需 skill 放入 `.codex/skills`、`.claude/skills`、`.cursor/skills`、`.agents/skills` 或 agent plugin cache。上述位置会造成自动发现、所有权混淆或依赖 agent 内部缓存结构。

## 按需入口 Skill

ArcForge 提供一个体积小、行为稳定的按需入口 skill。该入口本身安装在 agent 可发现的用户级原生 skill 目录中。

按需入口的触发边界只覆盖用户显式调用。普通业务任务、相似语义或 catalog 中某个 skill 的描述不能使入口自动搜索和加载按需 skill。

用户可以通过以下两类显式意图调用入口：

- 指定限定名称或明确 skill 名称并要求加载。
- 明确要求在 ArcForge 按需 catalog 中查找适合当前任务的 skill。

第二类调用只在入口已经被显式触发后进行候选判断。Agent 的日常 skill 路由不读取 catalog 候选，也不承担是否使用这些 skill 的判断成本。

按需入口不是独立任务执行器。它解析 catalog、选择一个确定的 skill 目录、读取该 skill 的 `SKILL.md` 和所需引用，然后由当前 agent 按已加载指令继续当前任务。

当 agent 平台提供原生的动态 skill 调用能力时，入口可以使用平台能力完成等价加载；没有原生能力时，入口按标准的“解析、完整读取、按指令执行”流程工作。两种方式必须选择相同的 catalog 条目并遵守相同的安全检查。

## 查找与优先级

按需入口只从用户级 catalog 中解析候选。

不同维护源存在同名 skill 时，系统不凭目录顺序静默选择。用户使用限定名称，或从入口给出的来源候选中明确选择。

名称和别名都无法唯一解析时，入口停止加载并返回可区分的候选。没有匹配项时，入口说明已检查用户级 catalog，并引导用户先通过 ArcForge 应用对应配置组。

按需入口不扫描任意文件系统目录来补充候选。只有 ArcForge catalog 索引中的有效条目可以被加载。

## 一致性与安全

按需 skill 与常驻 skill 都参与来源关系和漂移检查。漂移结果必须区分常驻目标和 catalog 目标。

入口在读取 skill 前校验索引路径位于声明的 catalog 根目录内，并校验内容摘要与索引一致。路径越界、索引损坏、内容漂移或目标缺失时，入口停止加载并提示用户执行 ArcForge drift 或重新应用。

入口不会提升当前 agent 权限，不会绕过系统、开发者、项目指令或工具确认边界。被加载 skill 请求的文件、网络、外部写入和破坏性动作继续使用当前 agent 的正常授权流程。

按需入口只读取完成当前显式调用所需的一个 skill 及其引用。它不会把整个 catalog 拼接到 prompt，也不会递归加载未被目标 skill 明确引用的其它 skill。

ArcForge 升级或重新应用按需入口时，确保同一个 agent 发现链上只有一个有效入口版本。同名冲突必须在应用计划中显示并在执行前解决。

## 目标变更

Skill 从 `ambient` 改为 `on-demand` 时，应用计划分别展示新增 catalog 副本和旧常驻副本。旧常驻副本属于需要确认的受管理清理项，不能仅因新副本应用成功而静默删除。

Skill 从 `on-demand` 改为 `ambient` 时，应用计划分别展示新增常驻副本和旧 catalog 条目。旧 catalog 条目同样通过受管理清理确认移除。

常驻 skill 的作用域从用户级改为项目级或从项目级改为用户级时，源位置和目标位置按两个独立应用关系处理。系统不会在未确认时删除另一作用域中的有效副本。按需 skill 不能变更为项目级作用域；它只能改为项目级常驻或保留用户级按需。

## 成功标准

维护者能够在正式 Skill 项目中长期维护项目默认和逐项推荐策略，并通过 Git review 和发布把推荐策略交付给使用者。

用户能够参考维护源推荐，并通过消费端配置或本次应用选择把 skill 最终应用为用户级常驻、项目级常驻或用户级按需。

按需 skill 不出现在 agent 的日常自动发现列表中，用户显式调用按需入口后可以稳定解析并加载它。

不同维护源中的同名按需 skill 不会相互覆盖或被静默选中。

用户能够从应用计划和漂移报告中确认每个 skill 的维护源、来源推荐、覆盖来源、最终策略、目标位置和内容一致性。

按需加载不改变 ArcForge 的产品边界：ArcForge 仍是本地优先、GitHub 优先的治理和预发布层，不成为公共 registry、托管 marketplace 或 agent runtime。
