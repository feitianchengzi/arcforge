# Skill 能力单元

维护目标 skill 前使用本文件。目标是先理解能力本身，再选择最小、合适的承载；不要预设 skill 与软件开发有关。

## 先分类，再选承载

skill 是 Agent 面向一类任务的交互入口和工作流契约。先由 Agent 根据真实场景判断能力性质，可以是：

- 知识与判断：提供领域概念、辨别标准、证据口径或决策方法。
- 方法与协作：规定提问、分析、确认、交接或复盘流程。
- 内容与创作：指导研究、写作、设计、翻译、策划或其他非代码产出。
- 工具集成：调用已有 CLI、API、MCP、应用或外部系统完成任务。
- 软件支撑：确实需要脚本、服务、UI、状态、schema 或测试设施。
- 混合能力：由以上多种承载共同完成，但每一种都必须有真实必要性。

分类是运行时语义判断，不写成代码中的领域枚举或关键词匹配。ArcForge 只提供通用目录、schema、校验、plan 和确认机制。

## 真实使用场景

创建或更新前，从用户输入中抽取 2 到 5 个代表性场景：

- 用户会怎样自然提出任务。
- Agent 首先需要理解或判断什么。
- 要读取哪些材料、工具结果或用户输入。
- 最终交付什么产物、状态、证据或下一步。
- 何时澄清、停止、请求确认或声明未知。

场景用于生成触发描述、门禁、reference 和验证任务，不把一次性项目名、客户名或临时偏好固化成通用规则。

## 目标 Skill 适配

候选 skill 足够匹配，需要同时考虑：任务领域、实际工作流、输入输出、不确定性处理和可重复验证。只覆盖背景知识、通用文档或某个实现工具的候选应作为辅助能力；没有足够匹配的目标 skill 时，再创建新的能力入口。

## 运行时与确定性机制的边界

应由 Agent 理解、分析、生成或判断的内容包括：

- 能力性质、真实场景和适用边界。
- 需要一个还是多个 skill，以及目标/辅助能力分工。
- 自然语言条件是否满足、证据是否充分、还需问什么。
- 是否需要工具、UI、状态或软件实现，以及采用何种已有承载。
- 内容质量、任务完成度和后续治理建议。

适合交给确定性工具的内容包括：

- JSON/YAML/schema 解析与结构校验。
- 路径包含关系、内容 digest、文件差异和来源记录。
- read-only plan、显式确认、事务写入、回滚和漂移报告。
- 对 Agent 或用户提交的结构化判断做绑定、完整性与安全边界校验。

工具没有充分证据时返回候选、未分类或需要输入；不得用名称、目录、关键词、数量、分数或固定业务规则替 Agent 下语义结论。

## 发现并选择实现承载

先搜索当前项目、用户提供的路径、已知仓库、已有 skill、CLI/API/MCP、应用、模板和数据模型。已安装 skill 目录是可读的运行副本或发现线索，不自动等于正式维护源；维护源需要 Git、ArcForge provenance、项目 manifest 或用户明确指定等证据。

发现已有承载后，由 Agent选择：

- 接入：已有能力足够，补清触发、输入输出和确认边界。
- 维护：修复已有实现，再同步 skill 契约。
- 包装：已有工具可用，但需要 skill 提供可发现入口和工作流。
- 新建：确认不存在合适能力，或复用成本明显更高时，创建最小承载。

如果继续会绑定错误接口或重复建设，向用户询问具体路径、命令或入口。

## 最小承载选择

- 只需 `SKILL.md`/reference：价值主要来自意图路由、判断方法、步骤或注意事项。
- 脚本/CLI：需要重复、参数化、结构化输出、dry run 或稳定校验。
- API/MCP/server：需要外部系统、长期任务、索引、缓存、订阅或跨会话状态。
- UI：需要用户看、选、改、排序、对比或确认，且对话逐项处理低效。
- 状态/schema：后续步骤需要消费前一步的结构化结果，或需要追踪来源和选择。
- fixture/测试：需要可重复验证关键路径、失败状态或兼容性。

这些不是固定清单。非软件 skill 不需要为了“完整”引入代码；软件支撑型 skill 也不能用更长的 Markdown 掩盖缺少的执行能力。

## 结构化回传

任何工具或 UI 承载都应说明输入、用户动作、结构化输出、保存或回传位置、取消/失败状态，以及 Agent 收到结果后的下一步。工具输出事实，Agent解释事实并决定任务语义。

最终汇报说明：能力性质、本轮承载、复用的已有实现、未采用其他承载的原因，以及仍需验证或治理的缺口。
